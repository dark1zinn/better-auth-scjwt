# Security and lifecycle review (Better Auth 1.7.18)

This review covers `better-auth-scjwt` as a replacement for Better Auth's native session transport: token cryptography, the Better Auth hook and session lifecycle, revocation, transport and CSRF boundaries, fingerprints, packaging, and the development and CI setup. Each finding below was reproduced against real Better Auth endpoints (memory adapter, `auth.handler` or `auth.api`) or read from the installed 1.7.18 source before it was changed, and each fix or coverage gap landed as its own conventional commit with its tests and documentation.

Baseline: `975c1c4` (merged to `main` as `b8a09c8`). Findings 25–28 come from a follow-up review of `main` at `2ee5c02`. Target: `better-auth`/`@better-auth/core` 1.7.18, `jose` 6.2.12, Bun 1.4.2, Node.js 24.

## Reviewed and not treated as defects

- **Revocation with cookie cache.** The before-hook resolves the session through `internalAdapter.findSession` before any endpoint runs, so a revoked session is signed out even with a fresh `session_data` cookie. Covered in `test/session-cache.test.ts`.
- **Cookie-cache contents.** In cookie placement Better Auth still emits `session_data`, which carries the session's IP address, User-Agent, and native token; the `compact` and `jwt` strategies are readable by whoever holds the cookie jar. This predates the keyed fingerprints and does not grant authentication under SCJWT. It is documented with a recommendation to use the `jwe` strategy rather than changed.
- **Per-request key import.** `computeFingerprint` imports the HMAC key on each call (at most twice per request, next to two store reads). Caching keys would keep raw secrets in a long-lived map for a negligible gain, so it was not adopted. Skipping re-binding for guard calls that discard response headers is not possible: Better Auth always requests headers from its endpoints internally.
- **Request-state key.** The before and after hooks share their per-request outcome through the request's `AuthContext` object. A before hook of another plugin that returned a replacement `context.context` would break that link; no installed Better Auth plugin does.
- **Token cryptography.** HS256 is pinned, the issuer is checked, `kid` only selects a configured Better Auth secret version (no trial decryption, no remote keys), claims are validated as finite JSON with prototype-safe accumulation, and the `sid`/subject/expiry/fingerprint checks run against the store. No signature, algorithm-confusion, key-selection, or prototype-pollution bypass was found. Adding `aud`/`typ` requirements was considered and not adopted: SCJWTs are only accepted by the instance whose secret and issuer signed them, and no cross-token confusion path was demonstrated.
- **Native `token` fields in response bodies.** Better Auth sign-up, sign-in, two-factor verification, and admin session listings return the opaque native session token in JSON. SCJWT does not rewrite these bodies because Better Auth's revoke endpoints consume them. That token does not authenticate in either placement: presented in the configured transport it fails SCJWT verification and the request is signed out; presented in the other transport it is ignored. The one plugin that would have accepted it, `bearer()`, is now refused (finding 19). It is still a session secret: treat these responses accordingly.
- **Fingerprint strength.** User-Agent and `Sec-CH-UA-Platform` are client-supplied and the IP depends on proxy configuration. When no IP resolves, the network signal is empty and `strict` binds only browser headers. This was kept for compatibility with server-to-server and IP-less deployments and is documented and tested rather than changed.
- **Tolerant fingerprint modes.** `dynamic` accepts a token replayed from another network with the victim's User-Agent and re-binds it to the new network; one signal at a time, a replayed token can therefore follow any device whose platform matches. `loose` keeps only session liveness, expiry, and custom claims. Both are opt-in trade-offs for privacy browsers, rotating networks, and mobile clients, not defects: re-binding never extends a session or revives an ended one, `strict` remains the default, and revoking the session ends every copy of the token.
- **`oneTimeToken()`.** Its one-time token is a bearer credential by design: whoever verifies it within its lifetime (three minutes by default) receives the session. Under SCJWT the redeemer receives a new SCJWT bound to its own device, generating one requires an authenticated SCJWT, and the token is single use. The native session token in the verify response body does not authenticate. Covered in `test/lifecycle-finalization.test.ts`.
- **Header placement and CSRF.** Bearer tokens are not ambient, so Better Auth does not origin-check them; CORS governs which origins can send `Authorization` or read `set-auth-token`.
- **`onResponse` finalization.** Moving issuance to `onResponse` would order it after every hook but skip direct `auth.api` calls, so the `init`-appended finalizer was chosen instead.

## Remaining boundaries and limitations

- The finalizer's position relies on Better Auth 1.7.18 appending `init`-returned plugins and running plugin after-hooks in order. A plugin that appends after-hooks behind it fails requests with a configuration error instead of issuing early. `onResponse` interceptors that rewrite authentication headers after the hook pipeline are outside this guarantee. Re-check this when upgrading Better Auth.
- A request that passed authentication before a revocation completed is not interrupted; every request evaluated afterwards is rejected. Nothing beyond Better Auth's own storage atomicity is implied.
- Two-factor coverage is limited to the OTP method; TOTP, backup codes, trusted devices, passkeys, and provider MFA are not exercised.
- Direct `auth.api` calls bypass Better Auth's HTTP origin and CSRF checks; applications that forward browser headers must validate `Origin` themselves.
- Each request costs a durable-row lookup plus Better Auth's `findSession` read. This is what makes revocation immediate and should not be optimized away without measurements.
- CI runs on GitHub for pull requests and pushes to `main`; making the `CI` check required in branch protection is repository-owner action.
